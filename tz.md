# Техническое задание для AI-агента: SnowTrino

## 1. Цель проекта

Разработать новое Python-приложение **SnowTrino** на базе FastAPI для создания, управления и мониторинга Trino-кластеров в различных облачных провайдерах.

Приложение должно предоставлять веб-интерфейс, в котором пользователь может:

1. Создавать Trino-кластеры в облаках.
2. Просматривать список кластеров и их текущее состояние.
3. Запускать, останавливать, масштабировать и удалять кластеры.
4. Подключаться к работающему кластеру через веб-интерфейс.
5. Вводить SQL-запросы и получать результаты выполнения.
6. Просматривать историю запросов, их статусы и ошибки.

Основной сценарий использования: пользователь открывает веб-приложение, создаёт Trino-кластер, дожидается его готовности, выполняет SQL-запросы к данным в Iceberg/S3 и затем останавливает или удаляет кластер.

## 2. Технологический стек

Использовать следующие технологии:

- **Python 3.11+**
- **FastAPI** — HTTP API и серверная логика.
- **Jinja2 + HTMX** — серверный рендеринг веб-интерфейса без необходимости создавать отдельное frontend-приложение.
- **SQLAlchemy 2.x** — ORM.
- **PostgreSQL** — хранение информации о кластерах, задачах и истории запросов.
- **Alembic** — миграции базы данных.
- **Terraform** — создание и изменение облачной инфраструктуры.
- **Helm** — развёртывание Trino в Kubernetes.
- **trino-python-client** — выполнение SQL-запросов через Trino HTTP API.
- **Docker Compose** — локальный запуск приложения и PostgreSQL.
- **pytest** — тестирование.
- **Ruff** — линтинг и форматирование кода.
- **mypy** — статическая проверка типов.

Не создавать отдельное React/Vue-приложение на первом этапе. Интерфейс должен оставаться простым, функциональным и удобным для разработчика.

Версии зависимостей необходимо зафиксировать в `pyproject.toml` или lock-файле.

## 3. Архитектура

Разделить приложение на следующие компоненты.

### 3.1. Web/API

FastAPI отвечает за:

- REST API;
- отображение веб-страниц;
- валидацию пользовательского ввода;
- запуск операций управления кластерами;
- получение статусов задач;
- отправку SQL-запросов в Trino.

HTTP-обработчики не должны синхронно ждать завершения длительных операций развёртывания инфраструктуры.

### 3.2. Cluster Manager

Отвечает за жизненный цикл кластеров:

- создание;
- запуск;
- остановка;
- изменение количества worker-узлов;
- удаление;
- получение текущего состояния.

Операции с инфраструктурой должны выполняться асинхронно относительно HTTP-запроса пользователя. При старте операции API возвращает идентификатор задачи, а интерфейс периодически получает её статус.

### 3.3. Infrastructure Providers

Создать абстракцию для облачных провайдеров.

Предусмотреть возможность поддержки:

- AWS;
- Azure;
- Google Cloud Platform.

Не реализовывать все три интеграции одновременно. В MVP полноценно реализовать один провайдер — AWS, а для остальных предусмотреть интерфейсы и понятные сообщения о том, что провайдер пока не поддерживается.

В качестве базовой архитектуры развёртывания использовать Kubernetes. Terraform управляет облачной инфраструктурой, а Helm — релизом Trino внутри Kubernetes.

При необходимости допускается реализация альтернативного способа развёртывания через отдельный адаптер провайдера.

### 3.4. Query Service

Отвечает за подключение к работающему кластеру Trino и выполнение SQL.

Использовать `trino-python-client`, а не запускать SQL через shell, CLI или Terraform.

Сервис должен:

- проверять доступность кластера;
- выполнять SQL-запросы;
- возвращать имена столбцов и строки результата;
- ограничивать время выполнения;
- обрабатывать ошибки соединения и SQL;
- поддерживать получение результатов постранично;
- сохранять историю запросов.

### 3.5. Database

Хранить в PostgreSQL:

- метаданные кластеров;
- задачи создания, изменения и удаления кластеров;
- историю SQL-запросов;
- статусы и сообщения об ошибках;
- время создания и обновления записей;
- параметры конфигурации, необходимые для повторного получения состояния инфраструктуры.

Не хранить в базе пароли облачных аккаунтов, приватные ключи и другие секреты в открытом виде.

## 4. Модель кластера

Для каждого кластера хранить следующие данные:

- `id` — внутренний UUID;
- `name` — уникальное в рамках приложения имя;
- `provider` — AWS, Azure или GCP;
- `region`;
- `status`;
- `endpoint` — URL Trino после создания;
- `kubernetes_cluster_id` или ссылка на используемый Kubernetes-кластер;
- `namespace`;
- `trino_version`;
- `worker_count`;
- `worker_cpu`;
- `worker_memory`;
- `coordinator_cpu`;
- `coordinator_memory`;
- `terraform_state_ref` — ссылка или идентификатор Terraform state;
- `created_at`;
- `updated_at`;
- `last_error`.

Статусы кластера:

- `pending` — ожидает обработки;
- `provisioning` — создаётся инфраструктура;
- `starting` — запускается Trino;
- `running` — готов к работе;
- `updating` — изменяется конфигурация;
- `stopping` — останавливается;
- `stopped` — остановлен;
- `deleting` — удаляется;
- `deleted` — удалён;
- `failed` — произошла ошибка.

Предусмотреть обработку промежуточных состояний и запрет несовместимых операций. Например, нельзя отправлять SQL-запрос в кластер, который находится в состоянии `stopped`.

Статус `running` должен означать не просто наличие облачных ресурсов, а подтверждённую готовность Trino принимать запросы.

## 5. Управление инфраструктурой

### 5.1. Создание кластера

Пользователь заполняет форму:

- имя кластера;
- облачный провайдер;
- регион;
- версия Trino;
- конфигурация coordinator;
- количество worker-узлов;
- CPU и память worker-узла;
- параметры каталога данных, если они необходимы.

После отправки формы приложение:

1. Валидирует параметры.
2. Создаёт запись кластера со статусом `pending`.
3. Создаёт фоновую задачу.
4. Подготавливает изолированную Terraform-конфигурацию.
5. Создаёт инфраструктуру.
6. Развёртывает Trino через Helm.
7. Дожидается готовности Trino.
8. Проверяет соединение с Trino.
9. Сохраняет endpoint и переводит кластер в `running`.

При ошибке сохранить диагностическую информацию и перевести задачу и кластер в соответствующие состояния ошибки.

### 5.2. Terraform

Использовать Terraform через отдельный сервис-адаптер.

Предусмотреть операции `init`, `plan`, `apply` и `destroy`.

Требования:

- отдельное состояние Terraform для каждого кластера;
- изоляция рабочих каталогов;
- блокировка параллельных операций над одним кластером;
- таймауты и корректное завершение дочерних процессов;
- безопасное формирование аргументов процессов без shell-интерполяции;
- сохранение журналов выполнения;
- возможность повторить неудачную операцию без создания дублирующей инфраструктуры;
- контроль версий Terraform и модулей.

Для локальной разработки разрешить local state. Архитектура должна позволять перейти на удалённый backend с блокировкой состояния, например S3 с поддерживаемым механизмом locking.

Не запускать Terraform непосредственно внутри HTTP-обработчиков.

### 5.3. Запуск и остановка

Реализовать операции запуска и остановки кластера.

Предусмотреть, что конкретная семантика остановки зависит от инфраструктуры. В Kubernetes MVP может реализовывать остановку через управляемое масштабирование компонентов до нуля либо другой документированный способ освобождения ресурсов.

Не обещать, что остановка сохраняет все ресурсы и одновременно полностью прекращает расходы. Различать остановку вычислений и удаление инфраструктуры.

### 5.4. Масштабирование

Реализовать изменение количества worker-узлов работающего кластера.

Пользователь задаёт новое количество worker-узлов, приложение проверяет допустимые значения и инициирует обновление Helm-релиза.

Изменение конфигурации должно выполняться через инфраструктурный слой, с отслеживанием статуса и обработкой ошибок.

Архитектуру проектировать так, чтобы в будущем можно было добавить автоматическое масштабирование.

### 5.5. Удаление

Удаление должно требовать подтверждения в веб-интерфейсе.

Перед удалением:

- убедиться, что кластер не занят несовместимой операцией;
- получить подтверждение пользователя;
- выполнить Terraform destroy или предусмотренный сценарий удаления;
- удалить или архивировать метаданные согласно принятой политике;
- сохранить журнал операции.

Если удаление завершилось частично, не помечать кластер как успешно удалённый без проверки состояния ресурсов.

## 6. Выполнение SQL-запросов

На странице каждого кластера создать SQL-консоль.

Пользователь вводит SQL, нажимает Run и видит:

- текст запроса;
- время начала;
- продолжительность выполнения;
- статус;
- число полученных строк;
- результат в виде таблицы;
- ошибку, если запрос завершился неудачно.

Использовать `trino-python-client`.

Соединение должно использовать endpoint и параметры подключения выбранного кластера. Не создавать отдельное соединение к облачной инфраструктуре для каждого SQL-запроса, если можно безопасно переиспользовать конфигурацию подключения.

Предусмотреть:

- ограничение времени выполнения;
- ограничение размера результата;
- постраничную выдачу строк;
- отмену запроса, если это поддерживается используемым клиентом и протоколом;
- отображение SQL-ошибок;
- историю запросов с возможностью повторного запуска.

Не ограничивать консоль только `SELECT`: Trino также поддерживает DDL и другие SQL-операции. Однако права пользователя и доступные операции определяются настройками самого Trino.

**Безопасность:** разрешать выполнение SQL только через Trino-клиент. Не передавать пользовательский текст в shell, Terraform или системные команды. Ограничивать доступ к консоли авторизацией и сетевыми правилами. Не публиковать административный endpoint Trino без защиты.

## 7. Работа с Iceberg и S3

Предусмотреть конфигурацию каталога Trino для работы с Apache Iceberg и объектным хранилищем S3.

В MVP достаточно поддержать один тип каталога, например Iceberg с AWS Glue Catalog и S3.

Конфигурация каталога должна задаваться параметрами и секретами окружения, а не жёстко кодироваться в Python.

Не создавать отдельную реализацию чтения Iceberg в приложении: запросы выполняются непосредственно Trino.

## 8. Веб-интерфейс

Создать следующие страницы.

### Dashboard

Показывать:

- общее количество кластеров;
- количество работающих кластеров;
- количество остановленных кластеров;
- количество кластеров с ошибками;
- последние операции.

### Clusters

Таблица кластеров со столбцами:

- Name;
- Provider;
- Region;
- Status;
- Trino version;
- Workers;
- Created at;
- Actions.

Действия:

- Details;
- Start;
- Stop;
- Scale;
- SQL Console;
- Delete.

Кнопки должны быть недоступны, если операция несовместима с текущим статусом.

### Create Cluster

Форма создания кластера с валидацией значений и понятными сообщениями об ошибках.

### Cluster Details

Показывать конфигурацию кластера, endpoint, состояние, последние операции и ошибки.

### SQL Console

Создать редактор SQL, кнопку запуска, индикатор выполнения и таблицу результатов. На первом этапе достаточно простого текстового редактора; полноценную интеграцию с Monaco Editor можно добавить позже.

### Operations

Показывать задачи создания, остановки, изменения конфигурации и удаления. Для каждой задачи отображать статус, время начала, продолжительность и доступный журнал выполнения.

Использовать HTMX для обновления статусов и результатов без полной перезагрузки страницы.

## 9. REST API

Предусмотреть следующие endpoints:

- `GET /api/v1/clusters` — список кластеров;
- `POST /api/v1/clusters` — создание кластера;
- `GET /api/v1/clusters/{cluster_id}` — информация о кластере;
- `POST /api/v1/clusters/{cluster_id}/start` — запуск;
- `POST /api/v1/clusters/{cluster_id}/stop` — остановка;
- `POST /api/v1/clusters/{cluster_id}/scale` — изменение количества workers;
- `DELETE /api/v1/clusters/{cluster_id}` — удаление;
- `GET /api/v1/clusters/{cluster_id}/health` — проверка готовности;
- `POST /api/v1/clusters/{cluster_id}/queries` — выполнение SQL;
- `GET /api/v1/clusters/{cluster_id}/queries` — история запросов;
- `GET /api/v1/operations/{operation_id}` — статус операции;
- `GET /api/v1/operations/{operation_id}/logs` — журнал операции.

Длительные операции возвращают `202 Accepted` и идентификатор задачи.

Для всех endpoints использовать Pydantic-схемы, корректные HTTP-коды и единый формат ошибок.

## 10. Фоновое выполнение операций

Не полагаться исключительно на `asyncio.create_task()` внутри FastAPI: задача может потеряться при перезапуске процесса.

Для MVP реализовать простой отдельный worker-процесс, который обрабатывает задачи из PostgreSQL. Использовать таблицу задач с полями статуса, типа операции, идентификатора кластера, времени создания, попыток выполнения и ошибки.

Предусмотреть:

- атомарный захват задачи;
- защиту от параллельной обработки одной задачи;
- повторные попытки для подходящих временных ошибок;
- таймауты;
- сохранение состояния после перезапуска приложения;
- журналирование всех этапов.

Не добавлять Redis, Celery или Kafka без необходимости. Архитектура должна позволять заменить механизм очереди в будущем.

## 11. Безопасность

На первом этапе приложение может работать в режиме одного администратора, но архитектура должна позволять добавить пользователей и разграничение доступа.

Обязательные требования:

- не хранить облачные ключи в исходном коде;
- использовать IAM roles или другие механизмы краткосрочных облачных credentials там, где это возможно;
- не возвращать секреты в API;
- не записывать секреты в логи;
- ограничивать доступ к Terraform state и журналам;
- валидировать все пользовательские параметры;
- не допускать произвольного выполнения системных команд через веб-интерфейс;
- защищать операции удаления и изменения инфраструктуры;
- предусмотреть авторизацию для веб-интерфейса и API перед использованием приложения вне локальной среды;
- не открывать Trino в публичную сеть без необходимости.

В README отдельно описать требования к облачным IAM-разрешениям и сетевому доступу.

## 14. Docker Compose и локальная разработка

Обеспечить запуск приложения локально через Docker Compose.

Локальный запуск должен включать:

- FastAPI;

Приложение должно запускаться даже без настроенных облачных credentials. В таком режиме интерфейс и API доступны, а создание настоящего кластера выдаёт понятную ошибку конфигурации.

## 16. Критерии готовности MVP

MVP считается готовым, если:

1. Приложение запускается локально по инструкции из README.
2. Можно открыть веб-интерфейс и просмотреть список кластеров.
3. В mock-режиме можно создать кластер, проследить переходы статусов, изменить число workers и удалить кластер.
4. Операции выполняются в фоне и сохраняют состояние при перезапуске приложения.
5. Реализован адаптер Terraform и Helm.
6. При наличии настроенного AWS-окружения можно создать настоящий Trino-кластер.
7. Для работающего кластера отображается доступный endpoint.
8. Можно выполнить SQL-запрос через веб-интерфейс и получить табличный результат.
9. Ошибки инфраструктуры и SQL отображаются пользователю без утечки секретов.
10. Unit-тесты выполняются без облачных credentials.
11. В README описаны архитектура, настройка, запуск, тестирование, требования к IAM и удаление ресурсов.
